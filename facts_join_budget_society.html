Joining two facts: deduplicated athlete count + approved budget per request

How to show, in one visual, a unique athlete count (no male/female double-counting) alongside approved budget — filter-reactive, with no measure inflated.

Fact Adwh_aa_fact_athlete
Fact Bdwh_aa_fact_support_request_spo
EngineSPICE
Budget dedup keysupport_request_code

One dataset at athlete grain: FULL OUTER JOIN the athlete fact (primary) with the support-request fact (secondary) on support_request_code. Athlete count = distinctCount(athlete_code) (native dedup). Budget = sum(approved_share) — each request's full amount, counted once per support_request_code, never partial.

Step 1 — Build the dataset & the join

In the Dataset editor (Data prep) add both tables and define a single join. Table order matters for performance:

Primary table
dwh_aa_fact_athlete — the larger one. The primary table is not subject to the size limit.
Secondary table
dwh_aa_fact_support_request_spo — one row per request, small.
Join type
FULL OUTER on support_request_code
Why FULL OUTER
Keeps requests with no athletes (union / European-championship) — their budget must still be counted.
Why the athlete fact is primary The SPICE 20 GB join limit applies only to the combined secondary tables. The athlete fact as Primary isn't counted against it — put the large table as Primary and the limit becomes practically irrelevant. (Source: AWS — Joining data)
Note A SPICE join is computed and materialized at refresh time, not at view time — the fan-out cost is paid once per refresh; dashboard interaction stays fast. The join's "unique key" toggle does nothing in SPICE (direct-query only) — don't rely on it; correctness comes from the calculated fields below.
Step 2 — Calculated fields

After a FULL OUTER join, on athlete-less-request rows the athlete-fact columns are NULL, and vice-versa. So build "unified" keys/dimensions with coalesce that exist on every row. Note: after a join, columns with the same name in both tables get a source suffix — pick the copy from the correct table.

Unified key & grouping dimensions

src_key + dims (coalesce)
// dedup key — present on every row (incl. athlete-less requests)
src_key = coalesce({support_request_code[request]}, {support_request_code})

// grouping axes — request-side wins on matched rows, athlete-side as fallback
authority_dim = coalesce({authority_name[request]}, {authority_name})
society_dim   = coalesce({society_name[request]},   {society_name})
branch_dim    = coalesce({branch_name[request]},    {branch_name})
// ...add as needed: association_dim, support_request_year, etc.

Measure 1 — unique athlete count (native)

athlete_cnt
athlete_cnt = distinctCount({athlete_code})

athlete_code is unique per person, so distinctCount collapses the double report (same person once as male, once as female) automatically, recomputing over exactly the rows that survived filters. Athlete-less-request rows arrive with athlete_code = NULL → contribute 0. No unpivot needed: the fact is already at athlete grain with a gender column.

Measure 2 — approved budget, counted once per request

approved_share (recommended)
approved_share = {approved_amount} / countOver({src_key}, [{src_key}], PRE_AGG)

// in the visual use:  sum(approved_share)

The divisor is the number of athlete rows of that request after filters (PRE_AGG). So rows × amount/rows = the full amount — a request gets its whole budget whenever at least one of its athletes survives, and 0 when none do. Dedup is strictly by support_request_code, no other field.

This IS "each request counted once" sum(approved_share) for a single request = approved_amount exactly. Per authority/society = the exact sum of its requests, each once. The fraction exists only at the hidden (athlete) row grain, which you never display.
Step 3 — Using it in visuals
  • Athlete count: drop in athlete_cnt (already aggregated — do not wrap in SUM).
  • Budget: drop in approved_share with Sum aggregation.
  • Grouping axes: always the unified authority_dim / society_dim / branch_dim, not the raw columns.
  • Sort by budget: possible because everything is in one dataset — set sum(approved_share) as the sort field (descending); bars show athlete_cnt.
The TLV check Filter some societies + authority = Tel Aviv → athlete rows drop → distinctCount recomputes (fewer athletes) and approved_share re-sums (fewer requests). Both react, no double-count, no manual sync.
Step 4 — Why it works (rationale)
ProblemSolutionWhy robust
Gender double report (same person male+female) → male_cnt+female_cnt inflateddistinctCount(athlete_code)athlete_code unique per person → native collapse, reacts to every filter
1→many join inflates approved_amount (repeats per athlete row)divide by countOver(...PRE_AGG) then sumconstant per request → reconstitutes to the full amount, once
Filter surfaces only some rows of a request (e.g. age)PRE_AGG recomputes after the filteralways full if ≥1 survives · 0 if none — never partial
Athlete-less requests (union/Europe) get droppedFULL OUTER + coalescearrive with athlete_code=NULL → 0 in count, full budget (divisor = 1)
Why not a native budget SUM? A native SUM needs a request-grain base — but then the deduplicated athlete count can't react to athlete-level filters (gender/age). One measure always crosses grain; we chose to keep budget whole and exact, and the dedup count is the one that forces athlete grain. QuickSight has no Tableau-style SUM(FIXED), so "sum-distinct-by-key" must be realized via the share (divide) or a flag (appendix).
Step 5 — Governance rules (mandatory)
  1. Hide the raw approved_amount in the dataset (Restrict / Exclude) and expose only approved_share as "Approved budget". So no one accidentally SUMs the inflated copy. Footgun #1
  2. Only group budget by request-level dimensions — authority / society / union / branch / geography. All of a request's rows share one value there → the full amount lands in the correct bucket.
  3. Never put budget on an athlete-level axis (gender/age): a single request would split across buckets (share splits proportionally; flag dumps it all into one arbitrary bucket). The total is right but the breakdown is meaningless for a request-level measure.
Step 6 — Validation

Before publishing, build a scratch table grouped by support_request_code:

validation
// per request:  sum(approved_share)  must equal  approved_amount
Group by: support_request_code
Value:    sum(approved_share)   ==   min(approved_amount)

If it ties out at request grain, it's exact at every coarser grouping (authority/society) automatically. Also check: global sum(approved_share) = the known total budget.

Best practices

  • Athlete fact = Primary — sidesteps the 20 GB secondary-tables cap.
  • Hide raw request-level measures (approved_amount and the other request scores) — so nobody SUMs the inflated copy.
  • Drop unused string columns before ingest — strings dominate logical size (24B + text vs 12B numeric/date), and the fan-out repeats each string per athlete row.
  • Refresh: the FULL OUTER is recomputed each refresh; at this scale it's trivial.
Appendix — alternative: full amount on a single row (flag)

If you want the row-level value to stay whole (not a fraction), put the full amount on one representative row per request and 0 on the rest. Dedup is still by support_request_code; athlete_id is only a tiebreaker to pick the row, not a dedup key.

budget_once (alternative)
budget_once = ifelse(
   isNull({athlete_id})                                // athlete-less request = its only row
   OR {athlete_id} = minOver({athlete_id}, [{src_key}], PRE_AGG),
   {approved_amount}, 0)

// in the visual: sum(budget_once)

Warning Do not dedup by athlete_code in the flag — the double report (male+female) repeats athlete_code within a request ⇒ two rows ⇒ double budget. The tiebreaker must be a unique-per-row key (athlete_id). That's why the default is approved_share — it depends on no unique key at all.

Open question to confirm: is athlete_id unique per row in the athlete fact (a different id for the male-row and the female-row of the same person)? If yes → budget_once is valid. If not → use approved_share.

שלב 1 — בניית ה-Dataset וה-Join

בעורך ה-Dataset (Data prep) מוסיפים את שתי הטבלאות ומגדירים join יחיד. סדר הטבלאות קריטי לביצועים:

טבלה ראשית (Primary)
dwh_aa_fact_athlete — הגדולה. הטבלה הראשית אינה כפופה למגבלת הגודל.
טבלה משנית (Secondary)
dwh_aa_fact_support_request_spo — שורה אחת לבקשה, קטנה.
סוג Join
FULL OUTER על support_request_code
למה FULL OUTER
שומר גם בקשות ללא ספורטאים (איגוד / אליפות אירופה) — התקציב שלהן חייב להיכלל.
מדוע פקטת הספורטאים היא הראשית מגבלת ה-20 GB של join ב-SPICE חלה רק על סכום הטבלאות המשניות. פקטת הספורטאים כ-Primary אינה נספרת במגבלה — שמים את הגדולה כ-Primary והמגבלה כמעט בלתי-רלוונטית. (מקור: AWS — Joining data)
שים לב ה-join ב-SPICE מתבצע ומתממש בזמן ה-Refresh, לא בזמן צפייה. עלות ה-fan-out משולמת פעם אחת לרענון; אינטראקציית המשתמש בדשבורד מהירה. הגדרת ה-"unique key" ב-join לא משפיעה על SPICE (רלוונטית ל-Direct query בלבד) — אל תסתמכו עליה; הנכונות מגיעה מהשדות המחושבים למטה.
שלב 2 — שדות מחושבים (Calculated fields)

לאחר join מסוג FULL OUTER, בשורות של בקשה-ללא-ספורטאים העמודות של פקטת הספורטאים יהיו NULL, ולהפך. לכן בונים מפתחות/ממדים "מאוחדים" (coalesce) שקיימים בכל שורה. הערה: אחרי join, עמודות בעלות שם זהה בשתי הטבלאות מקבלות סיומת מקור — בחרו את העותק מהטבלה הנכונה.

מפתח וממדי קיבוץ מאוחדים

src_key + dims (coalesce)
// מפתח הדדופ — קיים בכל שורה (גם בקשה ללא ספורטאים)
src_key = coalesce({support_request_code[request]}, {support_request_code})

// צירי קיבוץ — request-side מנצח בשורות מותאמות, athlete-side כגיבוי
authority_dim = coalesce({authority_name[request]}, {authority_name})
society_dim   = coalesce({society_name[request]},   {society_name})
branch_dim    = coalesce({branch_name[request]},    {branch_name})
// ...הוסיפו לפי הצורך: association_dim, support_request_year וכו'

מדד 1 — ספירת ספורטאים ייחודית (מדדפקת)

athlete_cnt
athlete_cnt = distinctCount({athlete_code})

athlete_code ייחודי לאדם, לכן distinctCount מכווץ אוטומטית את הדיווח הכפול (אותו אדם פעם כזכר ופעם כנקבה), ומחושב מחדש בדיוק על השורות ששרדו את הפילטרים. שורות של בקשה-ללא-ספורטאים מגיעות עם athlete_code = NULL → תורמות 0 לספירה. לא צריך unpivot: הפקטה כבר ברזולוציית ספורטאי עם עמודת מגדר.

מדד 2 — תקציב מאושר, נספר פעם אחת לכל בקשה

approved_share (מומלץ)
approved_share = {approved_amount} / countOver({src_key}, [{src_key}], PRE_AGG)

// בוויזואל משתמשים ב:  sum(approved_share)

המחלק הוא מספר שורות הספורטאים של אותה בקשה אחרי פילטרים (PRE_AGG). לכן rows × amount/rows = הסכום המלא — הבקשה מקבלת את מלוא תקציבה בכל פעם שלפחות ספורטאי אחד שלה שרד, ו-0 אם אף אחד לא. הדדופ הוא אך ורק לפי support_request_code, ללא שדה נוסף.

זה בדיוק "כל בקשה נספרת פעם אחת" sum(approved_share) לבקשה בודדת = approved_amount במדויק. לכל רשות/אגודה = סכום מדויק של הבקשות שלה, כל אחת פעם אחת. השבר קיים רק ברמת השורה הנסתרת (ספורטאי) שלעולם לא מוצגת.
שלב 3 — שימוש בוויזואלים
  • ספירת ספורטאים: גררו athlete_cnt (כבר מצטבר — אין לעטוף ב-SUM).
  • תקציב: גררו approved_share עם צבירה Sum.
  • צירי קיבוץ: תמיד authority_dim / society_dim / branch_dim (המאוחדים), לא העמודות הגולמיות.
  • מיון לפי תקציב: אפשרי כי הכול ב-Dataset אחד — הציבו sum(approved_share) כשדה המיון (יורד), והברים מציגים athlete_cnt.
בדיקת ה-TLV סינון חלק מהאגודות + רשות=ת"א → שורות ספורטאים יורדות → distinctCount מחשב מחדש (פחות ספורטאים) ו-approved_share מסתכם מחדש (פחות בקשות). שניהם מגיבים, ללא כפילות וללא סנכרון ידני.

שלב 5 — כללי ממשל (חובה)
  1. הסתירו את approved_amount הגולמי ב-Dataset (Restrict / Exclude), וחשפו רק את approved_share בשם "תקציב מאושר". כך אף אחד לא יסכום בטעות את העותק המנופח. Footgun #1
  2. קבצו תקציב רק לפי ממדים ברמת בקשה — רשות / אגודה / איגוד / ענף / גיאוגרפיה. כל שורות הבקשה חולקות ערך יחיד בממדים אלה → הסכום המלא נוחת בדלי הנכון.
  3. אל תשימו תקציב על ציר ברמת ספורטאי (מגדר/גיל): בקשה בודדת תתפצל בין דליים (share מפצל יחסית; flag זורק להכול לדלי אחד שרירותי). הסה"כ נכון אך הפירוק חסר-משמעות למדד ברמת בקשה.
